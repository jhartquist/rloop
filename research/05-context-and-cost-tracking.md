# Research: Context Window Tracking and Cost Reporting

## Context

rloop's `context_usage` MCP tool is hardcoded to return `0.0%`. The `TokenAccumulator` in `step.rs` sums token counts across the stream but the resulting percentage is wrong because it naively adds per-message values that are already cumulative. Meanwhile, the SDK provides `total_cost_usd` on the Result message, but we have no independent cost model to verify it or break it down by token type. This research defines exactly how Claude API token metrics work, how to compute accurate context percentage, and how to build a cost model.

---

## 1. Token Types: What Each Counter Means

The Claude API usage object contains four token fields per message:

```json
{
  "input_tokens": 8,
  "cache_creation_input_tokens": 5317,
  "cache_read_input_tokens": 32714,
  "output_tokens": 457
}
```

### 1.1 `input_tokens`

Tokens in the request that were **neither cached nor used to create a cache entry**. This is the "uncached" portion of the input. In many conversations with prompt caching, this can be very small (single digits) because most of the system prompt and conversation history hits the cache.

**Critical insight:** `input_tokens` is NOT the total input to the model. It is the residual after subtracting cached tokens. The total input is:

```
total_input = input_tokens + cache_read_input_tokens + cache_creation_input_tokens
```

### 1.2 `cache_read_input_tokens`

Tokens served from the prompt cache. These are tokens the model still "sees" and processes — they consume context window capacity just like regular input tokens — but they cost 90% less because the server doesn't need to re-encode them.

### 1.3 `cache_creation_input_tokens`

Tokens that were written to the cache during this request. These also consume context window capacity and cost 25% more than base input (for 5-minute TTL) or 100% more (for 1-hour TTL).

### 1.4 `output_tokens`

Tokens generated by the model in this turn's response. Output tokens count toward the context window because they become input history in subsequent turns.

### 1.5 The Fundamental Equation

**All four token types count toward context window consumption:**

```
context_used = input_tokens + cache_read_input_tokens + cache_creation_input_tokens + output_tokens
```

This is the total number of tokens the model is working with in a single turn — the full conversation history (input side) plus the response it generates (output side).

### 1.6 Per-Message vs. Cumulative

This is the central confusion that causes bugs in context tracking:

| Source | Semantics | Use For |
|--------|-----------|---------|
| `assistant_message.usage` | **Per-turn** token counts for that specific API call | Context window tracking |
| `result_message.usage` | **Cumulative** totals across all turns in the session | Billing / total cost |

**The per-turn `input_tokens` on an assistant message already includes the full conversation history up to that point.** It is NOT incremental. Each turn's input includes: system prompt + all prior messages + new user message + tool definitions. As the conversation grows, `input_tokens` (+ cache variants) grows with it.

This means:
- **Summing `input_tokens` across turns is WRONG for context tracking** — it over-counts massively.
- **The last assistant message's usage reflects the current context consumption.**
- **Summing `input_tokens` across turns IS correct for billing** — each API call genuinely processes that many input tokens.

### 1.7 Real Data Example

From an actual rloop session log (archive), consecutive messages in the same API call:

```
Turn 1: input_tokens=10, cache_creation=16303, cache_read=16411, output=1
Turn 2: input_tokens=8,  cache_creation=5317,  cache_read=32714, output=1
```

Turn 2's `cache_read` grew because turn 1's cache_creation tokens are now cache_read tokens. The total input for turn 2 is `8 + 5317 + 32714 = 38039`, which is the full context at that point.

## 2. Context Window Sizes

All current Claude models have a **200,000 token** default context window:

| Model | Context Window | Max Output | 1M Beta |
|-------|---------------|------------|---------|
| Claude Opus 4.6 | 200K | 128K | Yes |
| Claude Sonnet 4.5 | 200K | 64K | Yes |
| Claude Sonnet 4 | 200K | 64K | Yes |
| Claude Haiku 4.5 | 200K | 64K | No |
| Claude Opus 4.5 | 200K | 64K | No |
| Claude Opus 4.1 | 200K | 32K | No |
| Claude Opus 4 | 200K | 32K | No |

The 1M beta requires a special header (`context-1m-2025-08-07`) and triggers premium pricing beyond 200K tokens. rloop does not use the 1M beta, so **200K is the correct baseline for all models**.

### 2.1 Context Awareness (Sonnet 4.5, Haiku 4.5)

These models receive built-in context tracking from the API:

```
<budget:token_budget>200000</budget:token_budget>
```

After each tool call, the model sees:

```
<system_warning>Token usage: 35000/200000; 165000 remaining</system_warning>
```

This is automatic for these models. Older models (Opus 4, Sonnet 4, etc.) do not have this. Our `context_usage` tool supplements or replaces this for models that lack built-in awareness.

### 2.2 The SDK's `modelUsage.contextWindow` Field

The Agent SDK's Result message includes a `modelUsage` map with a `contextWindow` field per model. This tells us the context window size dynamically rather than hardcoding it:

```typescript
// From the SDK result:
const contextWindowSize = Object.values(result.modelUsage)[0]?.contextWindow ?? 200000;
```

However, the Rust SDK (`claude-agent-sdk-rs`) may not expose this field. If available, use it. If not, 200K is the correct default.

## 3. Context Percentage Calculation

### 3.1 The Bug Today

Current code in `step.rs`:

```rust
fn compute_context_usage(total_input: u64, total_output: u64) -> Event {
    const CONTEXT_WINDOW: f64 = 200_000.0;
    let used = (total_input + total_output) as f64;
    let percentage = ((used / CONTEXT_WINDOW) * 100.0) as f32;
    // ...
}
```

And in `extract_result_usage`:
```rust
let total_input = usage.get("input_tokens") + usage.get("cache_read_input_tokens") + usage.get("cache_creation_input_tokens");
let total_output = usage.get("output_tokens");
```

This is called with values from the **Result message**, which has **cumulative** totals. Adding cumulative input + cumulative output double-counts because the cumulative input already includes all prior outputs (they became input in subsequent turns).

The `TokenAccumulator` also sums across all messages, which compounds the over-counting.

### 3.2 Approach A: Last Message's Usage (Recommended)

**Use the most recent assistant message's usage to compute context percentage.**

Since each assistant message's `input_tokens` (+ cache variants) reflects the full conversation history at that point, the last message tells us the current context state:

```rust
struct ContextTracker {
    /// Most recent per-turn usage (from last assistant message).
    last_input_tokens: u64,
    last_cache_read: u64,
    last_cache_create: u64,
    last_output_tokens: u64,
}

impl ContextTracker {
    fn update_from_assistant_usage(&mut self, usage: &serde_json::Value) {
        self.last_input_tokens = usage.get("input_tokens").and_then(|v| v.as_u64()).unwrap_or(0);
        self.last_cache_read = usage.get("cache_read_input_tokens").and_then(|v| v.as_u64()).unwrap_or(0);
        self.last_cache_create = usage.get("cache_creation_input_tokens").and_then(|v| v.as_u64()).unwrap_or(0);
        self.last_output_tokens = usage.get("output_tokens").and_then(|v| v.as_u64()).unwrap_or(0);
    }

    fn context_percentage(&self) -> f32 {
        const CONTEXT_WINDOW: f64 = 200_000.0;
        let total = (self.last_input_tokens + self.last_cache_read + self.last_cache_create + self.last_output_tokens) as f64;
        ((total / CONTEXT_WINDOW) * 100.0) as f32
    }
}
```

**Why this works:** The API reports token usage per API call. Each call sends the full conversation history. So the last call's input tokens = current size of the conversation on the input side. Adding `output_tokens` from that same message gives the total context consumed by that turn.

**Why include `output_tokens`:** The output is part of the context window during generation. The model cannot generate more output than `context_window - input_tokens`. And once the turn completes, those output tokens become part of the input for the next turn.

**Limitation:** Between turns, context can only be known from the most recent turn. But that's fine — context only matters at decision points (when the agent is working).

### 3.3 Approach B: Cumulative Approximation

If we can't reliably distinguish per-message vs. cumulative usage in the SDK's message stream, we can approximate:

```rust
fn approximate_context(cumulative_input: u64, cumulative_output: u64, num_turns: u32) -> f32 {
    // The last turn's input ≈ cumulative_input / num_turns * num_turns
    // This doesn't work well because input grows non-linearly
    // (each turn adds more history)

    // Better: last turn's input ≈ cumulative_output (all prior outputs become input)
    // + base_prompt_tokens (system prompt, tools, etc.)
    // This is still an approximation.

    // Simplest: just use the cumulative input from the Result message directly,
    // since it's the total from the last API call (which includes full history).
    todo!()
}
```

This approach is fragile and not recommended. Approach A is definitively correct.

### 3.4 Approach C: Token Counting API

Anthropic provides a free `/v1/messages/count_tokens` endpoint that accepts the same message format and returns the token count without making an API call. This could be used to get exact context consumption at any point.

```rust
// Before each turn, count tokens:
let count = client.count_tokens(messages).await?;
let percentage = (count.input_tokens as f64 / 200_000.0) * 100.0;
```

**Pros:**
- Exact, authoritative count
- Accounts for tokenizer differences and edge cases
- Free (separate rate limits from messages API)

**Cons:**
- Extra API call per turn (latency)
- May not be available through the SDK abstraction (Claude Code SDK manages the conversation internally)
- Adds complexity

This is a good verification/debugging tool but probably overkill for real-time tracking.

### 3.5 Recommendation

**Use Approach A (last assistant message's usage) for real-time context tracking.**

The formula:

```
context_percentage = (input_tokens + cache_read + cache_create + output_tokens) / 200_000 * 100
```

Where all values come from the **most recent assistant message's usage**, not cumulative sums.

### 3.6 Message Deduplication

The SDK may send multiple assistant messages with the same message ID (e.g., text + tool_use in the same turn). These have **identical usage**. When updating the context tracker, deduplicate by message ID to avoid processing the same usage data multiple times.

```rust
struct ContextTracker {
    last_message_id: Option<String>,
    // ...
}

impl ContextTracker {
    fn maybe_update(&mut self, message_id: &str, usage: &serde_json::Value) {
        if self.last_message_id.as_deref() == Some(message_id) {
            return; // Same turn, same usage
        }
        self.last_message_id = Some(message_id.to_string());
        self.update_from_assistant_usage(usage);
    }
}
```

Note: In the current rloop code, the Rust SDK's `Message::Assistant` may or may not expose a message ID directly. If not, we can use the presence of a `usage` field change as a heuristic for a new turn, or track whether usage has changed from the last seen values.

## 4. Wiring Context Tracking into the `context_usage` Tool

### 4.1 The Problem

The `context_usage` MCP tool is a closure created at tool-build time. It currently returns hardcoded `0.0%`. It needs access to the context tracker, which is updated during stream processing.

### 4.2 Approach A: Shared State via Arc<Mutex> (Like `complete` Tool)

The `complete` tool already uses `Arc<Mutex<Option<String>>>` for the summary and `Arc<AtomicBool>` for the stop flag. The context tracker can follow the same pattern:

```rust
// In tools.rs:
pub struct ToolState {
    pub summary: Arc<Mutex<Option<String>>>,
    pub stop: Arc<AtomicBool>,
    pub context_percentage: Arc<AtomicU32>,  // f32 bits stored as u32
}

fn build_context_usage_tool(context_pct: Arc<AtomicU32>) -> SdkMcpTool {
    tool!("context_usage", "...", schema, move |_args| {
        let pct = f32::from_bits(context_pct.load(Ordering::SeqCst));
        let recommendation = match pct {
            p if p < 50.0 => "plenty of room",
            p if p < 70.0 => "getting full, consider wrapping up",
            p if p < 90.0 => "running low, wrap up soon",
            _ => "critical, finish immediately",
        };
        async move {
            Ok(tool_ok(json!({ "percentage": pct, "recommendation": recommendation }).to_string()))
        }
    })
}
```

In `step.rs`, after each assistant message:

```rust
// Update the shared context percentage
let pct = context_tracker.context_percentage();
tools.state.context_percentage.store(pct.to_bits(), Ordering::SeqCst);
```

**Pros:**
- Follows existing pattern (Arc shared state)
- Lock-free (AtomicU32 for f32)
- Simple

**Cons:**
- The context tool reads whatever was last written — could be slightly stale
- Adds another field to `ToolState`

### 4.3 Approach B: Callback-Based Update

Instead of shared state, pass a callback that the stream processor calls to update the tool:

```rust
let context_updater = Arc::new(Mutex::new(0.0f32));
let tool_ref = Arc::clone(&context_updater);

// In tool closure:
let pct = *tool_ref.lock().unwrap();

// In stream processor:
*context_updater.lock().unwrap() = new_percentage;
```

This is functionally identical to Approach A but uses a Mutex instead of atomics. Slightly simpler types but marginally slower.

### 4.4 Recommendation

**Use Approach A (Arc<AtomicU32>).** It matches the existing `stop: Arc<AtomicBool>` pattern and is lock-free.

## 5. Cost Model

### 5.1 Current Pricing (February 2026)

Pricing per million tokens (MTok):

| Model | Input | Output | Cache Write (5m) | Cache Read |
|-------|-------|--------|-------------------|------------|
| Haiku 4.5 | $1.00 | $5.00 | $1.25 | $0.10 |
| Sonnet 4.5 | $3.00 | $15.00 | $3.75 | $0.30 |
| Sonnet 4 | $3.00 | $15.00 | $3.75 | $0.30 |
| Opus 4.6 | $5.00 | $25.00 | $6.25 | $0.50 |
| Opus 4.5 | $5.00 | $25.00 | $6.25 | $0.50 |
| Opus 4.1 | $15.00 | $75.00 | $18.75 | $1.50 |
| Opus 4 | $15.00 | $75.00 | $18.75 | $1.50 |

Cache write pricing:
- 5-minute TTL (default): 1.25x base input price
- 1-hour TTL: 2.0x base input price

Cache read pricing: 0.1x base input price (for all TTLs)

### 5.2 Cost Formula

```
cost = (input_tokens * input_price / 1_000_000)
     + (output_tokens * output_price / 1_000_000)
     + (cache_creation_input_tokens * cache_write_price / 1_000_000)
     + (cache_read_input_tokens * cache_read_price / 1_000_000)
```

Where `input_price`, `output_price`, `cache_write_price`, and `cache_read_price` are per-MTok values for the specific model.

### 5.3 Important: We Don't Need to Calculate Cost

The SDK's Result message already provides `total_cost_usd`, which is authoritative. We use this for the session summary. The cost formula is useful for:

1. **Breakdown by token type** — showing where money went (e.g., "80% cache reads, 15% output, 5% input")
2. **Per-step cost estimates** — when we want to show cost as the step progresses (before the Result message)
3. **Verification** — sanity-checking the SDK's reported cost

### 5.4 Approaches to Price Management

**A. Hardcoded prices in code**

```rust
impl Model {
    fn input_price_per_mtok(&self) -> f64 {
        match self {
            Model::Haiku => 1.0,
            Model::Sonnet => 3.0,
            Model::Opus => 5.0,
        }
    }
    // ...
}
```

**Pros:** Simple, no config to manage, works offline.
**Cons:** Requires code change + release when prices change. Anthropic changes prices occasionally (typically downward).

**B. Config-driven prices**

```toml
# .rloop/config.toml
[pricing.haiku]
input = 1.0
output = 5.0
cache_write = 1.25
cache_read = 0.10

[pricing.sonnet]
input = 3.0
output = 15.0
cache_write = 3.75
cache_read = 0.30

[pricing.opus]
input = 5.0
output = 25.0
cache_write = 6.25
cache_read = 0.50
```

**Pros:** Users can update without code changes. Supports custom/enterprise pricing.
**Cons:** Config complexity. Users must manually update prices.

**C. Rely solely on SDK's `total_cost_usd`**

Don't maintain our own price table at all. Use the SDK's authoritative cost.

**Pros:** Always correct, zero maintenance.
**Cons:** No breakdown by token type. No running cost estimate during stream (only available at end). Cannot verify independently.

### 5.5 Recommendation

**Phase 1: Rely on SDK's `total_cost_usd` (Approach C).** This is what we do today and it works. The Result message provides total cost and we report it in `StepResult.cost_usd`.

**Phase 2: Add hardcoded prices (Approach A) for cost breakdown.** When we want to show "input: $X, output: $Y, cache: $Z" in session summaries, add a simple price table. Keep it as a const table in `model.rs` since our `Model` enum only has three variants and maps to specific pricing tiers.

**Phase 3 (optional): Config-driven prices (Approach B).** Only if users request it or if Anthropic starts changing prices frequently.

### 5.6 Note on Cache Write TTL

The Claude Agent SDK / Claude Code appears to use 1-hour cache writes for system prompts and tool definitions (based on the session log data showing `ephemeral_1h_input_tokens`). This means cache_creation_input_tokens are charged at 2.0x base input, not 1.25x. However, we don't control this through the SDK — it's an implementation detail of the Claude Code platform. For cost breakdown, we may need to assume a TTL or check the `cache_creation.ephemeral_1h_input_tokens` field if available.

## 6. Fixing the Current Code

### 6.1 Changes Needed in `step.rs`

**Problem 1: `TokenAccumulator` sums across messages**

The current `TokenAccumulator` adds every message's token counts together. This is correct for billing (cumulative cost) but wrong for context tracking. We need two tracking mechanisms:

```rust
/// Tracks cumulative tokens for billing/reporting.
struct TokenAccumulator {
    input_tokens: u64,
    output_tokens: u64,
    cache_read_tokens: u64,
    cache_creation_tokens: u64,
}

/// Tracks current context usage from the latest turn.
struct ContextTracker {
    last_input: u64,
    last_cache_read: u64,
    last_cache_create: u64,
    last_output: u64,
}
```

Wait — actually, the `TokenAccumulator` is summing per-message usage values from `Message::Assistant`. But if `input_tokens` on each assistant message represents the *full* conversation history for that turn, then summing them gives "total input tokens billed across all turns" which is correct for billing. The SDK's Result message provides this same cumulative total.

So `TokenAccumulator` is correct for billing. We just need a separate `ContextTracker` that takes the **last** values instead of summing.

**Problem 2: `compute_context_usage` called with wrong inputs**

Currently called from `extract_result_usage` using cumulative totals from the Result message. This should instead use the last assistant message's per-turn usage.

### 6.2 Changes Needed in `tools.rs`

Replace the hardcoded `0.0%` in `build_context_usage_tool` with a read from shared state (see Section 4).

### 6.3 Changes Needed in `log.rs`

No structural changes needed. The `Event::ContextUsage` type already captures percentage and recommendation. Just needs to be populated with correct values.

### 6.4 Summary of Changes

| File | Change | Size |
|------|--------|------|
| `step.rs` | Add `ContextTracker` struct; update from last assistant message's usage; pass to shared state | Medium |
| `step.rs` | Fix `compute_context_usage` to use last-message values, not cumulative | Small |
| `tools.rs` | Add `context_percentage: Arc<AtomicU32>` to `ToolState`; read it in `build_context_usage_tool` | Small |
| `tools.rs` | Update `create_tools` to create and return the shared atomic | Small |

### 7.3 Frequency of Context Updates

Emitting a `ContextUsage` event after every assistant message would be too noisy. Options:

1. **Every N turns** — e.g., every 5 turns. Simple but misses rapid growth.
2. **On threshold crossings** — emit when crossing 25%, 50%, 60%, 70%, 80%, 90%, 95%. Sparse and meaningful.
3. **On significant change** — emit when percentage changes by more than 5% from last report. Adaptive.
4. **Only when agent asks** — the `context_usage` tool returns it on demand, no unsolicited events. Cleanest.

**Recommendation:** Emit on threshold crossings (option 2) for terminal display, plus always respond accurately when the agent calls `context_usage` (option 4). The threshold crossing events serve as warnings for the human watching; the tool serves the agent's self-management.

### 7.4 Session Log Data

For later analysis, log every `TokenUsage` event (already done). Additionally, log a `ContextUsage` event after each turn so post-hoc analysis can plot context growth over time. This is separate from terminal display frequency.

## 8. The `TokenAccumulator` Question

### 8.1 Are Accumulated Totals Correct for `StepResult`?

`StepResult` stores: `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`. These come from `TokenAccumulator`, which sums all per-message token events.

**Question:** If each assistant message's `input_tokens` includes the full conversation history, summing them gives `sum(history_size_at_turn_i)` which is much larger than the actual input processed. Is this what we want for billing/reporting?

**Answer:** This is actually correct for billing. Each API call genuinely processes that many input tokens, and Anthropic charges for each call independently. The total cost is `sum(per_call_cost)`, which means `sum(per_call_input_tokens) * price` is the right formula for total input cost.

However, the SDK's Result message provides the cumulative totals and `total_cost_usd` directly. We should prefer those over our manual accumulation for two reasons:
1. The SDK handles deduplication (same message ID = same usage)
2. The SDK may include tokens we don't see (system prompt additions, tool definitions)

**Recommendation:** For `StepResult`, continue using the SDK's Result message values when available. Keep `TokenAccumulator` as a fallback and for live reporting during the stream.

### 8.2 SDK Deduplication

The SDK sends multiple `Message::Assistant` entries with the same message ID when Claude produces text + tool_use in the same turn. All have identical usage. Our `TokenAccumulator.add_from_event` is called for each, causing double/triple counting.

**Fix:** Track the last seen message ID and skip duplicate usage entries:

```rust
struct TokenAccumulator {
    input_tokens: u64,
    output_tokens: u64,
    cache_read_tokens: u64,
    cache_creation_tokens: u64,
    last_message_id: Option<String>,
}

impl TokenAccumulator {
    fn add_from_usage(&mut self, message_id: &str, usage: &serde_json::Value) {
        if self.last_message_id.as_deref() == Some(message_id) {
            return; // Already counted this turn
        }
        self.last_message_id = Some(message_id.to_string());
        // ... add tokens
    }
}
```

**Note:** The Rust SDK (`claude-agent-sdk-rs`) may or may not expose the message ID on `Message::Assistant`. If it does, use it. If not, we can detect duplicate usage by comparing the usage values themselves (identical values from same turn).

## 9. Extended Thinking Considerations

When extended thinking is enabled:
- Thinking tokens are billed as output tokens
- Previous turns' thinking blocks are **automatically stripped** from context by the API
- Current turn's thinking counts toward context window during generation

For context tracking, this means:
- The `input_tokens` on a message already excludes previous thinking (the API strips them before sending)
- The `output_tokens` includes thinking tokens for the current turn
- Our formula `input + cache_read + cache_create + output` remains correct because the API does the thinking-block management for us

No special handling needed in rloop.

## 11. Open Questions

### 11.1 Does the Rust SDK expose message IDs?

The `Message::Assistant` type in `claude-agent-sdk-rs` may or may not include the message `id` field. If it does, we can use it for deduplication. If not, we need an alternative deduplication strategy (e.g., tracking whether usage values changed).

**Impact:** Affects `TokenAccumulator` deduplication (Section 8.2) and `ContextTracker` updates.

### 11.2 Does the Rust SDK's `Message::Assistant.usage` include cache breakdown?

The current code in `step.rs` accesses `m.message.usage` as a `serde_json::Value`. We extract `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`. Need to verify these fields are actually present on per-message usage (not just the Result message).

**From session log data:** Yes, they are. The session log shows `cache_creation_input_tokens` and `cache_read_input_tokens` on every assistant message.

### 11.3 Should we include `output_tokens` in the context percentage formula?

**Arguments for:**
- Output tokens genuinely consume context window during generation
- The model cannot generate beyond `context_window - input_tokens`
- After the turn, output becomes input for the next turn

**Arguments against:**
- `input_tokens` on the *next* turn will already include this turn's output
- Double-counting in a sense: the output "uses" context during this turn, then again as input next turn
- Claude Code's formula (from codelynx.dev analysis) appears to use `input + cache_read + cache_create` without `output`

**Resolution:** This is a question of "what do we mean by context usage?"

- **"How full is the context right now?"** → Include output. During generation, the context window holds input + output. This is the number that determines whether the model can continue.
- **"How much of the context window is conversation history?"** → Exclude output. The input side is what's accumulated; output is ephemeral until it becomes next turn's input.

**Recommendation:** Include output tokens. This gives the most conservative (safest) estimate. When the agent asks "how much room do I have?", telling it the context including current output is more useful than telling it about input only. If context is at 80% including output, the agent knows it has ~40K tokens left, which accounts for the space needed for its next response.

### 11.4 What cache TTL does Claude Code use?

The session log shows `cache_creation.ephemeral_1h_input_tokens: 16303`, indicating 1-hour cache TTL. This affects cost breakdown calculations (2.0x vs 1.25x base input price).

**Impact:** If we add cost breakdown, we need to know the TTL to apply the right multiplier. Options:
- Check `cache_creation.ephemeral_1h_input_tokens` vs `ephemeral_5m_input_tokens` in usage data
- Default to 1-hour (what the SDK seems to use)
- Ignore and approximate (difference is modest)

### 11.5 Should we warn the agent at specific thresholds?

Options:
1. **Agent self-manages** — calls `context_usage` when it wants to know. No unsolicited warnings.
2. **System warns via tool result** — append context warnings to tool results at thresholds.
3. **Inject system messages** — add context warnings into the conversation. Not possible through the SDK.

**Recommendation:** Agent self-manages (option 1). The agent prompt already instructs it to call `context_usage`. Adding unsolicited warnings would complicate the message flow and the agent already has built-in context awareness on newer models (Sonnet 4.5, Haiku 4.5).

### 11.6 How does the `compute_context_usage` call flow work today?

Currently `compute_context_usage` is called from `extract_result_usage`, which is only called when processing the `Message::Result`. This means context percentage is only computed once, at the very end of the step. By then it's useless — the step is over.

**Fix:** Call context tracking updates from `Message::Assistant` processing, not from `Message::Result`. The Result message is used for final cumulative billing totals; context tracking should happen in real-time during the stream.

### 11.7 Should we store context percentage in `StepResult`?

Currently `StepResult` has token counts but no context percentage. Adding `peak_context_percentage: f32` would be useful for post-hoc analysis of which tasks are context-heavy.
