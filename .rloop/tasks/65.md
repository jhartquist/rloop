# Research axum API design patterns for the brain

## Context

The brain is an axum HTTP server that coordinates workers and serves clients (CLI, TUI, web). It needs REST endpoints for commands and WebSocket for live event streaming. We need to understand axum patterns before building.

## Research Questions

1. **App structure**: How to organize an axum app with multiple route groups (projects, sessions, tasks, queue, workers, events)? Router composition, state sharing, middleware.

2. **State management**: The brain holds DB connection pool, active session state, connected WebSocket clients. How does axum handle shared mutable state? `Arc<AppState>` pattern? What goes in state vs what's passed per-request?

3. **WebSocket support**: How does axum handle WebSocket upgrades? Broadcasting to multiple clients? Filtering events per subscription? What happens when a client disconnects?

4. **Error handling**: Consistent error responses across endpoints. How to map anyhow errors or domain errors to HTTP status codes + JSON error bodies.

5. **Graceful shutdown**: How to handle Ctrl+C, drain connections, notify workers. Integration with tokio signal handling.

6. **Testing**: How to test axum handlers? Integration tests with a real server? Mock state?

7. **Middleware**: Auth (API key), CORS, request logging. How to layer these in axum.

## Deliverable

Write findings to `docs/research/axum-brain.md`. Include skeleton code for the app structure, a representative endpoint, and the WebSocket broadcast pattern.

## Acceptance Criteria

- App structure recommendation with code skeleton
- WebSocket broadcast pattern documented
- Error handling strategy decided
- State management pattern chosen
- Graceful shutdown approach
