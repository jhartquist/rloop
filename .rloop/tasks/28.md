# Fix context usage calculation bug

## Problem

Context usage is reporting percentages over 100% (up to 1942% in session 20260207-162003.jsonl). The current calculation in `step.rs:305-308` adds:
- `input_tokens`
- `cache_read_input_tokens`
- `cache_creation_input_tokens` ← **should NOT be included**
- `output_tokens` ← **should NOT be included**

This gives cumulative session token totals, not the actual context window usage at a given turn.

## Root Cause

From Claude API token accounting:
- `input_tokens`: new tokens sent in this turn
- `cache_read_input_tokens`: tokens loaded from cache (already in context)
- `cache_creation_input_tokens`: tokens being marked for caching (subset of input, not additive)
- `output_tokens`: tokens generated by the model (output, not input context)

The context window only contains **input tokens that are actually loaded**, which is:
```
input_tokens + cache_read_input_tokens
```

`cache_creation_input_tokens` marks which tokens to cache but they're already counted in `input_tokens`.
`output_tokens` are generated output, not input context.

## Fix Location

`rloop/src/step.rs:305-308` in `ContextTracker::update()`:

```rust
// WRONG:
let used = (input + cache_read + cache_create + output) as f64;
let pct = ((used / CONTEXT_WINDOW) * 100.0) as f32;

// CORRECT:
let used = (input + cache_read) as f64;
let pct = ((used / CONTEXT_WINDOW) * 100.0) as f32;
```

## Acceptance Criteria

1. Update `ContextTracker::update()` to calculate context percentage using only `input_tokens + cache_read_input_tokens`
2. Remove `cache_creation_input_tokens` and `output_tokens` from the calculation
3. Run existing tests — they should still pass (this is a bug fix, not behavior change)
4. Add a test case that verifies context percentage calculation:
   - Given: input=10k, cache_read=50k, cache_create=5k, output=2k
   - Expected: (10k + 50k) / 200k * 100 = 30%
   - Not: (10k + 50k + 5k + 2k) / 200k * 100 = 33.5%
5. Verify the context_usage tool in `tools.rs` reads the corrected percentage (it already does, no changes needed there)

## Background Context

Session logs show context percentages like:
- 388%, 883%, 1765%, 1942%

These numbers represent total session token throughput, not per-turn context window usage. With a 200k context window, even long sessions shouldn't exceed 100% on a single turn unless there's a calculation error.
