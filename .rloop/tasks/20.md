Research how Claude API token metrics (input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens) relate to the context window size and cost. Today we accumulate these numbers but the `context_usage` tool is hardcoded at 0.0%. The goal: accurate real-time context tracking and comprehensive cost reporting.

## Approach

Use parallel research agents to explore these aspects simultaneously:

1. **Token types and context window math** — Research exactly what each token counter means in the Claude API. How input_tokens, cache_read_input_tokens, and cache_creation_input_tokens relate to each other and to the context window. Whether output_tokens count against the context window (they do — the conversation grows). How the context window is actually consumed turn by turn (system prompt + conversation history + tools). Whether the 200k number is the right baseline for all models or varies. How Claude Code itself tracks context (it shows a percentage — reverse-engineer the formula).
2. **Cost calculation** — Current per-token pricing for each Claude model (Haiku, Sonnet, Opus). How cache tokens affect cost (cache reads are cheaper than fresh input). Build a cost model: `cost = (input * input_price) + (output * output_price) + (cache_read * cache_read_price) + (cache_creation * cache_creation_price)`. Whether cost per model should be hardcoded, configurable, or fetched. How to keep prices up to date as Anthropic changes them.
3. **Real-time context tracking in step.rs** — Today `TokenAccumulator` sums tokens across the stream. Research how to compute an accurate context percentage from these accumulated values. The challenge: input_tokens per message includes the full conversation history (it is not incremental), so naive summing over-counts. Research whether the SDK provides cumulative vs. incremental usage. How to wire the computed percentage into the `context_usage` MCP tool so the agent gets real data.
4. **Reporting and display** — How to present token and cost data at step, task, and session levels. What the terminal output should look like (current format vs. improvements). Whether to show context percentage in a progress bar. How to break down cost by category (input, output, cache) in the session summary. What data to log for later analysis of context efficiency across tasks.

## Output

Write `research/05-context-and-cost-tracking.md` with sections for:
- Definitive explanation of each token type and how they compose into context usage
- Cost formulas per model with current pricing
- Multiple approaches to real-time context percentage calculation (cumulative vs. incremental, per-message vs. per-turn)
- Trade-offs (accuracy vs. simplicity, hardcoded prices vs. configurable)
- Open questions to resolve before implementation (is input_tokens cumulative or incremental per message, how does caching affect context window consumption, should we warn the agent at specific thresholds or let it self-manage)
