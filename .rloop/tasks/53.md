Several production code paths use .expect() which panics instead of returning errors:

- session.rs:211: `.expect("futures should not be empty")` in the DAG execution loop
- tools.rs:210: `.lock().expect("summary lock poisoned")` in MCP tool handler
- step.rs:197: `.lock().expect("summary lock poisoned")`
- testing.rs:30,51,89: `.lock().expect("results lock poisoned")`

## What to do

- session.rs:211: Replace with `.ok_or_else(|| anyhow!("internal error: futures empty in DAG loop"))??`
- tools.rs:210: Return a tool error instead of panicking on poisoned mutex
- step.rs:197: Use `.lock().map_err(|_| anyhow!("internal: mutex poisoned"))?`
- testing.rs: These are test utilities so .expect() is more acceptable, but if testing.rs ships as a public module, consider error handling
- Ensure all tests pass

## Why

The coding conventions say no .unwrap() outside tests. expect() is effectively unwrap() with a message. Panicking in production code is unacceptable — these should return errors.
