## Goal

Harden parallel execution for production use: Ctrl+C cleanup, readable terminal output with concurrent tasks, comprehensive integration tests, and optional CLI override.

## Reference

Read `research/06-parallel-dag-implementation.md` for the full design spec. Phases 1-3 (tasks 31-33) must be complete.

## Changes

### 1. Ctrl+C with parallel tasks

In `main.rs`, verify that the existing `tokio::select!` + `cleanup_worktrees` pattern correctly handles multiple concurrent worktrees. The existing cleanup scans `.rloop/worktrees/` and removes everything — this already handles multiple worktrees. Verify that dropping the `FuturesUnordered` (via select cancellation) properly drops in-flight Claude client futures. Add a brief grace period if needed.

Write a test or manual verification that Ctrl+C during parallel execution leaves no orphaned worktrees or branches.

### 2. Task ID prefix in terminal output

When `max_parallel > 1`, events from concurrent tasks interleave in the terminal. Add a `[task XX]` prefix to `StreamPrinter` output (in `step.rs` or `log.rs`) so humans can distinguish which task produced which output. Only add the prefix when `max_parallel > 1` to avoid noise in sequential mode.

### 3. Comprehensive integration tests

Using the mock executor pattern, add tests that exercise the full parallel pipeline:
- **Diamond DAG parallel:** 0 → {1, 2} → 3 with `max_parallel=2`. Verify 1 and 2 run concurrently (use timing or atomic counters in mock).
- **Wide independent DAG:** 5 tasks, no deps, `max_parallel=3`. Verify max 3 in-flight at any time.
- **Merge conflict with merge-fix:** Mock executor writes conflicting files, verify merge-fix agent is attempted.
- **Failure propagation:** Task fails mid-flight, verify independent sibling completes, dependents skipped.
- **All-tasks parallel:** `run_all_session_with` with `max_parallel > 1`.
- **Session metrics:** Verify metrics aggregate correctly across parallel tasks.

The mock executor needs enhancement: `FileWritingMockExecutor` that writes specified files in the worktree, enabling merge conflict scenarios.

### 4. Optional `--parallel N` CLI flag

Add `--parallel <N>` to the `run` subcommand in `main.rs`. Overrides `max_parallel` from config. Useful for one-off parallel runs without editing config.

```
rloop run 05 --parallel 2
rloop run --all --parallel 3
```

### 5. Documentation

Update the default `.rloop/config.toml` template (in `config.rs`) to include the `[session]` section with `max_parallel` commented out. Ensure `rloop init` produces a config that documents the option.

## Approach

Use subagents for independent work: (a) Ctrl+C verification + cleanup, (b) terminal output prefixing, (c) integration tests, (d) CLI flag. These are largely independent and can be parallelized.

## Acceptance Criteria

- Ctrl+C during parallel execution cleans up ALL worktrees and branches
- Terminal output distinguishes concurrent tasks with `[task XX]` prefix
- Comprehensive test suite covers all parallel execution scenarios
- `--parallel N` CLI flag works and overrides config
- `rloop init` template documents `max_parallel`
- All tests pass (92+ existing + new parallel tests)
- `cargo clippy --all-targets -- -D warnings -W clippy::pedantic` clean
- No data races or panics under concurrent execution
