## Goal

Replace the sequential `for` loop in `execute_dag` with a `FuturesUnordered`-based parallel scheduler. Merge strategy is rebase-then-fast-forward. Merge conflicts result in task failure (merge-fix agent comes in Phase 3).

## Reference

Read `research/06-parallel-dag-implementation.md` for the full design spec. Phase 1 (task 31) must be complete first — this builds on `EventSender`, `find_ready_tasks`, and `max_parallel` config.

## Changes

### 1. New git helpers

In `git.rs`, add:
- `rebase(repo, branch, onto) -> Result<()>` — runs `git rebase <onto> <branch>`, returns error on conflict
- `rebase_abort(repo) -> Result<()>` — runs `git rebase --abort`

Unit test both with real git repos (create conflicting commits, verify rebase succeeds/fails).

### 2. Branch preservation for merge-failed tasks

Modify `cleanup_worktree` in `git.rs` — add a `preserve_branch: bool` parameter (or a separate `cleanup_worktree_preserve_branch` function). When true, remove the worktree directory but skip `git branch -D`. Log a message about the preserved branch.

### 3. New event variant

In `log.rs`, add `Event::MergeFailed { task_id, branch, reason }`. Add terminal printing and JSONL serialization for it.

### 4. Parallel scheduler in `execute_dag`

Replace the `for` loop with:
```
loop {
    // Fill frontier up to max_parallel (lazy worktree creation)
    while in_flight.len() < max_parallel {
        if let Some(task_id) = next from find_ready_tasks(...) {
            spawn task future into FuturesUnordered
        } else { break }
    }
    if in_flight.is_empty() { break }

    // Await next completion
    let (task_id, outcome) = in_flight.next().await
    // Serialize merge via tokio::sync::Mutex
    // Rebase worktree branch onto session branch, fast-forward on success
    // On conflict: rebase_abort, mark as failed, preserve branch
}
```

Key details:
- Semaphore with `max_parallel` permits controls concurrency
- Worktree creation is lazy (after acquiring permit, branch off latest session branch HEAD)
- Merge serialized via `tokio::sync::Mutex` — only one rebase+fast-forward at a time
- `max_parallel=1` degenerates to sequential (no separate code path)
- Failed tasks go in `failed_set`, dependents skipped (same semantics as today)
- Merge-failed tasks treated as task failures

### 5. Tests

Write tests using the existing `MockExecutor` pattern:
- Diamond DAG: 0 → {1, 2} → 3; verify 1 and 2 can run in parallel
- Wide DAG: 5 independent tasks, `max_parallel=2`, verify throttling
- Failure mid-flight: task fails while sibling runs, sibling completes, dependents skipped
- `max_parallel=1`: existing tests all pass through new code path
- Merge conflict: mock executor writes conflicting files, second merge fails, branch preserved

The mock executor may need enhancement to write files in the worktree (for merge conflict tests). Add a `FileWritingMockExecutor` or extend the existing one.

## Approach

Use subagents to conserve context. For example: (a) git helpers + tests, (b) event variant + logger updates, (c) scheduler rewrite + tests. The scheduler rewrite is the largest piece and should be done carefully in a single focused session.

## Acceptance Criteria

- Parallel execution works: independent tasks run concurrently up to `max_parallel`
- `max_parallel=1` produces identical behavior to previous sequential execution
- Merge conflicts detected: task marked as failed, branch preserved for manual recovery
- `Event::MergeFailed` logged and printed
- All existing tests pass (they implicitly use max_parallel=1)
- New tests cover: diamond DAG, wide DAG, failure mid-flight, merge conflict, throttling
- `cargo clippy --all-targets -- -D warnings -W clippy::pedantic` clean
