# Research Supabase local dev workflow and migration strategy

## Context

Milestone 1 replaces file-based tasks with Postgres via Supabase. Before building, we need to understand the local dev workflow and decide on a migration strategy.

## Research Questions

1. **Local dev setup**: What does `supabase init` + `supabase start` actually do? What Docker containers run? What ports? How much resource overhead? How to start/stop cleanly?

2. **Migration strategies**: Supabase offers multiple approaches:
   - Raw SQL migration files (`supabase/migrations/*.sql`)
   - Schema-based strategy where you define the schema and migrations are auto-generated
   - sqlx's own migration system (`sqlx migrate`)
   - Which approach works best when the Rust app uses sqlx for compile-time checked queries?

3. **sqlx migrations vs supabase migrations**: Can they coexist? Should migrations live in sqlx (closer to the Rust code) or in supabase (closer to the DB)? What are the tradeoffs?

4. **Service configs**: Supabase has services beyond Postgres — storage, auth, RLS, edge functions. Do we need migration/config management for any of these in M1? Or can we defer entirely?

5. **Dev workflow**: What does the daily dev cycle look like? Start supabase, run brain, run tests, stop supabase. How do you reset the DB? Seed data?

## Deliverable

Write findings to `docs/research/supabase-local-dev.md`. Include concrete recommendations, not just options.

## Acceptance Criteria

- Clear recommendation on migration strategy (sqlx vs supabase vs hybrid)
- Local dev workflow documented step by step
- Service config question answered (do now vs defer)
- Any gotchas or surprises noted
