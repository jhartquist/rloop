Research how to evolve rloop from sequential single-task execution to parallel DAG execution and eventually daemon mode. Today `execute_dag` runs tasks one at a time in a for loop. The goal: run independent tasks concurrently (capped at 2-3) and optionally run as a long-lived daemon that picks up tasks automatically.

## Approach

Use parallel research agents to explore these aspects simultaneously:

1. **Parallel DAG execution** — How to identify independent tasks in the DAG and run them concurrently. Tokio task spawning vs. join sets. How to cap concurrency (semaphore, channel, configurable max_parallel). How session branching and merging works when multiple worktrees are active (each worktree branches off session branch, but merges must be serialized). Error propagation when one parallel task fails and others are in-flight. How the logger handles interleaved events from concurrent tasks.
2. **Daemon mode architecture** — Separating the submit-work CLI from the execute-work daemon. How the daemon discovers new or changed tasks (filesystem watch vs. polling vs. explicit signal). Session lifecycle when the daemon is always running. How to report status (socket, file, log). `rloop watch <task-id>` or `rloop status` commands. Graceful shutdown.
3. **Compilation contention** — Multiple Rust agents compiling in parallel worktrees will fight over CPU and possibly cargo target dirs. Research cargo workspace strategies, sccache, target dir isolation. Practical limits on parallelism for Rust projects specifically. Whether 2-3 is the right cap or if it should be configurable per-project.
4. **Future cloud workers (Hetzner)** — Eventually daemons will run on remote Hetzner machines pulling code and tasks from a central source. Research what abstractions we need now to avoid painting ourselves into a corner. Task storage (files vs. database vs. hybrid). Whether the daemon should be git-centric (pull repo) or API-centric (fetch tasks from a service). How session branches work with multiple machines.

## Output

Write `research/02-parallel-dag-and-daemon.md` with sections for:
- Multiple approaches for parallel execution (tokio tasks, bounded channels, actor model)
- Multiple approaches for daemon mode (systemd service, background process, socket-activated)
- Trade-offs for each (complexity, reliability, debuggability, future cloud compatibility)
- Open questions to resolve before implementation (max parallelism strategy, daemon vs. no-daemon for v1, task storage format for multi-machine, whether to build parallel first or daemon first)
