Research the design of the Human Queue — the system that lets agents ask questions, log assumptions, propose tasks, and optionally block while waiting for human input. This is the core differentiating feature of rloop. The human never blocks the agent loop; instead, agents queue items and humans process them asynchronously in batches.

## Approach

Use parallel research agents to explore these aspects simultaneously:

1. **Agent-side tools and blocking semantics** — New MCP tools the agent gets: `ask_question`, `log_assumption`, `propose_task`. Each can be blocking (step pauses until human responds) or non-blocking (agent continues, answer available on retry). How blocking works with the step executor — does the step return a new status like `Blocked`? Does the session need resume capability? How to serialize and restore a blocked step. What happens to the worktree while blocked.
2. **Human-side interface and workflow** — The human processes a queue of items. Key UX insight: unlike Claude Code `AskUserQuestion` which batches questions and waits for all answers, HumanQ should show one item at a time and immediately dispatch each answer for processing. An LLM workflow processes each answer (creating follow-up questions or new tasks). Research TUI frameworks (ratatui) for the review interface. What the review flow looks like: see question, answer it, immediately see next item while previous answer is being processed. Also: reviewing proposed tasks (approve, reject, edit), reviewing assumptions (acknowledge, correct), reviewing code (optional human review of completed tasks).
3. **Queue storage and state machine** — Where queue items live (files in `.rloop/queue/`, SQLite, in-memory with persistence). State transitions: Pending -> InReview -> Answered -> Processed (or Pending -> Expired if task completes without needing the answer). How to handle stale items when a task fails or is retried. Schema for queue items (type, task_id, content, response, status, timestamps).
4. **Session resume and step continuation** — If a step blocks on a question, the session needs to be resumable. Research how to checkpoint a step (worktree state, conversation history, learnings so far). Whether to use Claude Code session resume or rebuild context from logs. How this interacts with the daemon model (daemon could automatically resume when answers arrive). The relationship between blocking questions and the DAG (does a blocked task block its dependents?).

## Output

Write `research/04-human-queue.md` with sections for:
- Multiple approaches to queue storage (files, SQLite, hybrid)
- Multiple approaches to blocking semantics (true block with resume, fake block with retry, non-blocking only for v1)
- Multiple approaches to the human review interface (TUI, CLI prompts, web UI later)
- The answer-processing LLM workflow design
- Trade-offs for each major decision (complexity, reliability, UX quality)
- Open questions to resolve before implementation (blocking vs non-blocking first, TUI vs CLI for v1, how queue interacts with daemon mode, whether to build resume capability or defer it)
