# Refine Postgres schema for Milestone 1

## Context

The ROADMAP.md has a sketch schema with four tables (projects, tasks, sessions, events). This needs refinement before implementation — proper indexes, constraints, enum handling, and sqlx compatibility.

## Research Questions

1. **Enum strategy**: Should `model`, `status`, `event_type` be Postgres ENUMs, TEXT with CHECK constraints, or plain TEXT? How does each option work with sqlx?

2. **depends_on as INTEGER[]**: How well does Postgres array type work with sqlx? Can you do compile-time checked queries with array operations (`ANY`, `@>`)? Or should dependencies be a separate join table?

3. **Events table design**: JSONB payload vs typed columns? The current `Event` enum has ~25 variants with different fields. Options:
   - `event_type TEXT` + `payload JSONB` (flexible, matches current serde approach)
   - Typed columns for common fields + JSONB for variant-specific data
   - Separate tables per event type (probably overkill)

4. **Indexes**: What queries will the brain run most? Task lookup by project, event lookup by session, ready tasks (incomplete + deps satisfied). Design indexes for these.

5. **Timestamps and ordering**: Events need strict ordering within a session. Use `BIGSERIAL` ID for ordering? Or `created_at` with sufficient precision? Both?

6. **Soft delete vs hard delete**: Should completed sessions be archived? Tasks marked deleted vs actually removed?

7. **Session state**: What additional columns does the sessions table need? Duration, cost metrics, error info? Or are these derived from events?

## Deliverable

Write findings to `docs/research/schema-design.md`. Include the refined CREATE TABLE statements and index definitions.

## Acceptance Criteria

- Final CREATE TABLE statements for all M1 tables
- Indexes defined with rationale
- Enum strategy decided
- depends_on approach decided (array vs join table)
- Events table design decided
- All decisions justified with sqlx compatibility in mind
